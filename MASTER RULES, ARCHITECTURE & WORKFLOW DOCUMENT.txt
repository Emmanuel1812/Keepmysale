## 1. PROJECT OVERVIEW

### What We Are Building
An AI-powered multi-channel (WhatsApp + Email) customer
support SaaS for Shopify e-commerce merchants. The core
differentiator is a "Smart Return Negotiation" engine that
proactively intercepts return requests and negotiates
partial refunds via conversational AI, saving merchants
reverse logistics costs.

### Architecture Pattern
- Standalone Next.js web application (NOT embedded Shopify app)
- Shopify App Store listing as thin OAuth installer
- Multi-tenant SaaS (one codebase, many merchants)
- Serverless API routes on Vercel
- Real-time webhooks from Bird (WhatsApp) and Amazon SES (Email)
- AI processing via OpenAI API
- PostgreSQL database via Supabase
- Payments via Mollie

### Core User Flows
1. Merchant installs via Shopify App Store → OAuth → Onboarding
2. Customer sends WhatsApp/Email message → AI classifies intent
3. WISMO: AI fetches order status from Shopify → auto-responds
4. Return request: AI triggers negotiation state machine
5. Merchant views all conversations in unified inbox dashboard
6. Analytics show tickets resolved, returns prevented, money saved

## 2. GOLDEN RULES (ALL AGENTS MUST FOLLOW)

### Code Standards
- Language: TypeScript ONLY. No plain JavaScript. Ever.
- Strict mode enabled in tsconfig.json
- All functions must have explicit return types
- All function parameters must be typed (no `any` type)
- Use `interface` for object shapes, `type` for unions/intersections
- Use `const` by default, `let` only when reassignment needed
- No `var` keyword. Ever.
- Async/await only. No .then() chains.
- All API responses must use the standardized response helper
- All errors must be caught and logged using the error handler
- No console.log in production code — use the logger utility
- Maximum function length: 50 lines. Extract helpers if longer.
- All database queries go through the data access layer (DAL)
  Never write raw SQL in API routes or components.

### Naming Conventions
- Files: kebab-case (e.g., `return-negotiation.ts`)
- Components: PascalCase (e.g., `UnifiedInbox.tsx`)
- Functions: camelCase (e.g., `calculateRefundOffer()`)
- Constants: SCREAMING_SNAKE_CASE (e.g., `MAX_NEGOTIATION_STEPS`)
- Database tables: snake_case plural (e.g., `conversations`)
- Database columns: snake_case (e.g., `created_at`)
- API routes: kebab-case (e.g., `/api/shopify/verify-webhook`)
- TypeScript interfaces: PascalCase with `I` prefix (e.g., `IMerchant`)
- TypeScript types: PascalCase with `T` prefix (e.g., `TMessageChannel`)
- Enums: PascalCase name, SCREAMING_SNAKE values
- Environment variables: SCREAMING_SNAKE_CASE with service prefix
  (e.g., `SHOPIFY_API_KEY`, `BIRD_API_KEY`, `OPENAI_API_KEY`)

6. DATABASE SCHEMA (PostgreSQL/Supabase)
CRITICAL RULES:
All tables MUST have id (UUID), created_at, updated_at
All foreign keys MUST have ON DELETE CASCADE or SET NULL (specify per table)
All tables MUST have Row Level Security (RLS) enabled
All merchant-owned data MUST include merchant_id column
Timestamps MUST be timestamptz (with timezone)
Use UUID v4 for all primary keys
NEVER store raw API tokens — always encrypt
Table: merchants
sql

  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  supabase_user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE,

  shop_name TEXT,
  email TEXT NOT NULL,

7. API ROUTE CONTRACTS
Standardized Response Format
ALL API routes MUST return this structure:

typescript
// Success
{
  "success": true,
  "data": { ... },
  "meta": { "page": 1, "total": 100 }  // optional
}

// Error
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Human readable message",
    "details": { ... }  // optional
  }
}
API Response Helper (use in ALL routes)
typescript
// src/lib/api-helpers.ts
export function apiResponse<T>(data: T, status = 200) {
  return NextResponse.json({ success: true, data }, { status })
}

export function apiError(
  code: string,
  message: string,
  status = 400,
  details?: unknown
) {
  return NextResponse.json(
    { success: false, error: { code, message, details } },
    { status }
  )
}
8. RETURN NEGOTIATION STATE MACHINE
text
STATES AND TRANSITIONS:

[Customer sends return intent message]
              ↓
    ┌─── INITIATED ───┐
    │                  │
    ↓                  │
[AI calculates optimal offer based on:        │
 - product_cost                                │
 - estimated_return_cost                       │
 - customer LTV                                │
 - merchant configured percentages]            │
    ↓                                          │
  OFFER_SENT (Step 1: e.g., 20% partial)      │
    ↓                                          │
  ┌──────────┬──────────┐                      │
  ↓          ↓          ↓                      │
ACCEPTED   REJECTED   NO_RESPONSE (48h)        │
  ↓          ↓          ↓                      │
COMPLETED  OFFER_SENT  ESCALATED               │
           (Step 2:    (to human)              │
            35% partial)                       │
              ↓                                │

9. MULTI-CHANNEL MESSAGE FLOW
text
INBOUND FLOW:

WhatsApp Message (via Bird webhook)
  → POST /api/webhooks/whatsapp
  → Verify Bird signature
  → Parse message payload
  → Find or create customer (by phone number)
  → Find or create conversation
  → Store message in messages table
  → Route to AI Service:
    → Classify intent
    → If WISMO → fetch order → auto-respond
    → If RETURN → check for active negotiation
      → If none → initiate negotiation
      → If active → process response to current offer
    → If FAQ → RAG search → auto-respond
    → If COMPLEX → escalate to human
  → Send response via Bird API

Email Message (via SES → SNS → webhook)
  → POST /api/webhooks/email
  → Verify SNS signature
  → Parse email (from, subject, body, attachments)
  → Find or create customer (by email address)
  → Find or create conversation
  → Store message in messages table
  → Route to SAME AI Service as WhatsApp
  → Send response via Amazon SES

OUTBOUND FLOW:

AI generates response
  → Check conversation channel
  → If WhatsApp → send via Bird API
  → If Email → send via Amazon SES
  → Store outbound message in messages table
  → Update conversation.last_message_at

CROSS-CHANNEL LINKING:
  → When creating customer, check if phone OR email
    matches existing customer for this merchant
  → If match → merge into single customer record
  → All conversations from both channels visible
    under one customer profile in the inbox

11. ERROR HANDLING STANDARDS
typescript
// ALL API routes must follow this pattern:

export async function POST(req: NextRequest) {
  try {
    // 1. Validate input
    const body = await req.json()
    const validated = MySchema.safeParse(body)
    if (!validated.success) {
      return apiError('VALIDATION_ERROR', 
        'Invalid input', 400, validated.error.flatten())
    }

    // 2. Authenticate
    const merchant = await getMerchantFromRequest(req)
    if (!merchant) {
      return apiError('UNAUTHORIZED', 
        'Authentication required', 401)
    }

    // 3. Business logic (via service layer)
    const result = await SomeService.doThing(validated.data)

    // 4. Return success
    return apiResponse(result)

  } catch (error) {
    // 5. Log and return generic error
    logger.error('POST /api/route failed', { error })
    return apiError('INTERNAL_ERROR', 
      'An unexpected error occurred', 500)
  }
}
